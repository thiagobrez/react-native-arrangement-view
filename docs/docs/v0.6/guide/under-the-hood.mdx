# Under the hood

iOS is straightforward: its Fabric Native Component hosts SwiftUI's `ArrangementView`, and delegates the pane placement to it.

Android doesn't have an equivalent API, so we created custom shadow nodes that interface with a native Kotlin view to arrange the panes in the shadow tree. A fold or a resize moves the panes without a React render.

These diagrams follow the lifecycle of an `ArrangementView` starting from your JavaScript to the native views. Steps numbered in **purple** run once, when the view first renders. Steps numbered in **teal** follow them, and run again whenever the view's size, the window or the hinge changes.

## iOS

<ThemedImage
  src="guide/arrangement-ios"
  alt="An ArrangementView on iOS: ArrangementView.ios.tsx and layout.ts in JavaScript, RNArrangementView.mm and RNArrangementPane.mm in Objective-C++, and ArrangementHost.swift in Swift, with numbered arrows for the steps below."
  width={760}
  height={576}
/>

1. Your app renders `<ArrangementView>`. `ArrangementView.ios.tsx` renders the native view with the two panes, primary first.
2. React commits, and Fabric mounts the native view, `RNArrangementView.mm`, and the panes, `RNArrangementPane.mm`, on the main thread.
3. `RNArrangementView.mm` hosts SwiftUI through `ArrangementHost.swift`, which puts the panes in SwiftUI's `ArrangementView`, in the split or overlay style. Before iOS 27.1, or with an older SDK, it uses the [fallback](./how-panes-are-arranged#fallback) instead.
4. When the view appears, and whenever its size, the window or the hinge changes, SwiftUI's `ArrangementView` places the panes. The library doesn't choose their frames.
5. `ArrangementHost.swift` hands each pane's new frame to `RNArrangementView.mm`.
6. `RNArrangementView.mm` passes the frame to its pane. `RNArrangementPane.mm` updates the pane's shadow node at once, so Yoga lays its React content out at that size and Fabric mounts it, all within SwiftUI's layout pass.
7. After the layout pass, `ArrangementHost.swift` reports where the panes ended up, and `RNArrangementView.mm` sends them to `layout.ts` as `onPanesChange`. `layout.ts` turns the frames into a layout and, only if that changed, calls `onArrangementLayoutChange` and updates `useArrangementLayout()`.

When a prop such as `arrangement` changes, `RNArrangementView.mm` passes it to the host, and SwiftUI places the panes again from step 4.

## Android

<ThemedImage
  src="guide/arrangement-android"
  alt="An ArrangementView on Android: ArrangementView.android.tsx and layout.ts in JavaScript, ArrangementShadowNodes.cpp and arrange.h in the C++ shadow tree, and ArrangementView.kt in Kotlin, with numbered arrows for the steps below."
  width={760}
  height={576}
/>

1. Your app renders `<ArrangementView>`. `ArrangementView.android.tsx` renders the native view, a view that fills its content box, and the two panes.
2. React commits. The view's shadow node, in `ArrangementShadowNodes.cpp`, places the panes, but nothing has been measured yet, so both are hidden.
3. Fabric mounts the native view, `ArrangementView.kt`, and its panes on the UI thread.
4. When Jetpack WindowManager reports a new window layout, or the view's size or position changes, `ArrangementView.kt` measures its content box, its window and the fold.
5. If any of them changed, it passes them over JNI to its shadow node, as an immediate state update. Fabric commits it at once, on the UI thread.
6. The shadow node runs the pane policy in `arrange.h`, and writes each pane's frame into its Yoga style.
7. Yoga lays out the panes, and Fabric mounts their new frames before step 5's update returns. The next frame shows them.
8. The shadow node sends the frames to `layout.ts` as `onPanesChange`. `layout.ts` turns the frames into a layout and, only if that changed, calls `onArrangementLayoutChange` and updates `useArrangementLayout()`.

When a prop such as `arrangement` changes, React's commit rebuilds the view's shadow node with the new props. Steps 6 and 8 run in that commit, and Fabric mounts the new frames on the UI thread afterwards.
